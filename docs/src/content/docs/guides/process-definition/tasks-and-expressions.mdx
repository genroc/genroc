Tasks can produce data and pass it on to the tasks that follow.
That is what the task `output` and expressions are for.

## Task output

```genroc-lsp
name: output-example
tasks:
  - id: task1
    output: 1
    switch: next

  - id: task2
    output: 2
    switch: next

  - id: task_sum
    output: "$: outputs.task1 + outputs.task2"
    switch: end
```

Task output defines what will be passed to following tasks.
If the output is defined, the following tasks can read it through the
`outputs.<task_id>` expression.

The `$:` prefix marks an expression, which we explain below.

## Expressions

Genroc supports expressions, which let you compute values dynamically and pass them from one task to another.
In an expression you can reference the following variables:

  - `input` - the process input defined by `input_schema`
  - `outputs.<task-id>` - output of any earlier task (if it defines one)
  - `self` - data about the current task, not available outside it (see [looping](#looping))
  - `config` - configuration values resolved from environment variables (we will get to this later)

You can also use basic operators like `==`, `!=`, `<`, `<=`, `>`, `>=`, `&&`, `||`, `??`.

Expressions can also compose objects or arrays:

```genroc
{name: "John"}        # returns object
["John", "Marie"]     # returns array
```

### `map` function

For working with arrays, genroc also supports `map` function.
It takes an array as a first argument and callback as second.
In callback you can transform the items into different shapes.

```genroc
$: map(names, (name) => { who: name })
# Array<names> -> Array<{who: string}>
```

### String template

This is a simple use case: it lets you compose a string value dynamically.

```genroc
"Hello ${input.user_name}!"
```

The value passed into a template must be a primitive value (string, number or boolean), and it cannot be null.

You can escape `${}` by doubling the `$`, e.g.:

```genroc
"Hello $${input.user_name}!"
```

### Expression of any type

By prefixing the string with `$: ` you are not creating a template. The whole expression result is
used and its type is preserved:

```genroc
"$: outputs.task1 + outputs.task2"  # integer
```

This way you can also pass whole objects, e.g.:

```genroc
"$: input"                          # { user_name: ... }
```

### Raw expressions

In `switch/case` fields a static value would make no sense,
so there is no `$:` or `${}` syntax, you write the expression directly:

```genroc
switch:
  - case: "input.user_name == 'Brenda'"
    goto: ...
```

The same syntax is used also for `on_error/case` fields, which we will discuss later.

### Numbers

Expressions support `+`, `-`, `*`, `/` and `%`. Numbers are arbitrary-precision decimals,
following the [General Decimal Arithmetic](https://speleotrove.com/decimal/) specification
(the one Python's `decimal` module implements), computed with the
[apd](https://github.com/cockroachdb/apd) library. Genroc keeps them exact, also when it only
passes them through, so a long id like `9007199254740993` arrives unchanged, which many
JSON tools don't guarantee.

`+`, `-` and `*` are exact, decimals included:

```genroc
0.1 + 0.2              # 0.3
0.1 + 0.2 == 0.3       # true
input.id + 1           # 9007199254740994
```

`/` is the only operator that rounds, to 34 significant digits (the precision of IEEE 754
decimal128), with ties rounded away from zero:

```genroc
1 / 3                  # 0.3333333333333333333333333333333333
2 / 3 * 3              # 2.0000000000000000000000000000000001
```

The way a number is written decides its type: `3` is an `integer`, `3.0` is a `number`.
`%` works on integers only, so `7 % 2` is fine and `7 % 2.0` is refused when you apply the
definition.

> A client reading results in JavaScript loses precision on large numbers in `JSON.parse`,
> so a long id can still break there, on the client's side.

## Looping

You can also use switch to create loops. We however need a way
to express a condition when to stop and keep track of current state.

```genroc-lsp
name: looper
# number of iterations as an input
input_schema:
  type: integer
tasks:
  - id: task1
    # counting the iterations (previous output + 1)
    output: "$: (self.previous ?? 0) + 1"
    switch:
        # looping condition
      - case: "self.output < input"
        goto: $task1
      - goto: end
```

This process takes input of single integer (number of iterations)
and then loops on `task1` while counting the number of iterations in the `output`
field. In the switch statement we compare the counter (task output) with
the required number of iterations (process input).

The counter lives in `self`:

  - `self.previous` - the output of the last run of this task, `null` on the first run (hence the `??`)
  - `self.output` - the output this run just produced, readable only in `switch`

Actions add `self.result`, which we get to in the next chapter.
Which slot can read which is in the [expressions reference](../../reference/definition/expressions.mdx).

## Shapes

Shapes are a convenient way to transform data.
The best example is the task `output` field.

### Fully static

A shape can be fully static in YAML, with no expressions at all.

```genroc
output:
  ok: true
```

### Combined

Define the object shape statically and pass the values dynamically.

```genroc
output:
  name: "$: input.user_name"
```

### Expression only

Because expressions can define objects, you can build the whole structure
in one expression, or pass a variable that already has the expected shape.

```genroc
output: "$: { name: input.user_name }"
```

## Slots

You can use shapes and expressions anywhere a dynamic value is expected.
In the examples above that is:

| Slot | Where | Syntax |
|---|---|---|
| `case` | `switch` | raw expression |
| `output` | `task` | shape |
| `output` | `process` | shape |

Every action and clause introduced later brings its own slots, e.g. a fetch `body` is a shape
and its `url` a string template, but the syntax is always one of these.

## Process output

A process can optionally define an output. It looks like this:

```genroc
tasks:
  - id: task_sum
    output: "$: outputs.task1 + outputs.task2"
    switch: end

output:
  sum: "$: outputs.task_sum"
```

It has the same shape and syntax as a task output. It is evaluated once the process
reaches `switch: end`. It cannot access `self`, as it is not part of any task.

The output is the contract for the outside world: it is what callers read,
and what a parent checks a child's result against.
Task outputs are internal — visible in `genctl detail`, 
but nothing outside is written against them.
