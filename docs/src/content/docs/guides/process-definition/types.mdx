Genroc requires you to validate input into the process,
so it always knows what shape of the data is allowed to enter.

## Why?

Durable processes are tricky, because they can survive for a long time.
Common scenario is that we are using multiple endpoints on our API. For example
one to fetch some information and other to mutate something.

The issue is that our api can change in the meantime. If we fetch some data, then
pause the process for a month and resume it, it will basically use our old API against
the new API.

A strict validation can't prevent these issues, but makes them easy to detect.

## Static checking and inference 

Because the inputs are typed we can statically check all the expressions
in the process and check if they are referencing only existing properties and
operations are performed on a correct types.

We can also infer expression types, so if you use expression to create a new
object type, genroc will automatically infer its type.

## Inferred context

Through inference Genroc creates a typed context for every task. Based on what
tasks were (or could have been) executed before it, we can check what exact outputs
can be accessed in the expressions.

This creates a continuous flow of types, through the process, so you always
know what outputs are accessible and what are their types.

## Nullability

Genroc distinguishes if the field can be null, it doesn't allow nullable fields
in templates and operations which don't make sense on `null` type (e.g. `<`).
If you want to use nullable value in these places you have to provide fallback value with `??` operator.

```genroc
url: "${input.server_url ?? 'http://localhost:1234'}/user"
```

You can also use `default` to fill in a missing value.

```genroc
input_schema:
  type: object
  properties:
    server_url:
      type: string
      default: http://localhost:1234
```
Even though the value is not required here, genroc knows it can never be null
inside the process, because if it's not provided by the user, the default value will be used.
Combining required and default is refused, because then default can never be applied.

This changes however if it's specified as `type: [string, "null"]`,
here user can pass `null` explicitly and the default value is not used in this case.

> Genroc has only one NIL value `null`, so in the expressions there is no difference between nullable and non-required values (they both contain `null`)

## Demonstration on a real example

```genroc
name: nudge-inactive-user
input_schema:
  type: object
  properties:
    user_id: { type: string }
  required: [user_id]
tasks:
  - id: load_user
    action:     # here action can access `input`
      type: fetch
      method: get
      url: "https://api.example.com/users/${input.user_id}"
      responses:
        200:
          type: object
          properties:
            email: { type: string }
            activated: { type: boolean }
          required: [email, activated]
    output:     # we can access `input` and `self{result, headers, status}` (coming from fetch)
      email: "$: self.result.email"
    switch:     # here we can access both `self.result` and `self.output` if we want (+ everything from before)
      - case: "self.result.activated"
        goto: end
      - goto: $nudge

  - id: nudge
    action:     # now `outputs.load_user` is available (output of the previous task)
      type: fetch
      method: post
      url: "https://api.example.com/emails"
      body:
        to: "$: outputs.load_user.email"
    output:
      nudged: true
    switch: end

output:
  email: "$: outputs.load_user.email"
  # nudge task might not run, so the output can be null
  nudged: "$: outputs.nudge.nudged ?? false"
```

> TIP: Install the [genroc vscode extension](https://marketplace.visualstudio.com/items?itemName=genroc.genroc)
  and copy the process above to a new definition. You can then hover any expression part and see what is its type.
  It will also show you errors live.

### Declaring what enters the process

In the example, there are two places where outside data enter the process - `input_schema` and `responses`.

Genroc automatically validates these data and then we can safely access them in expressions.

### Inferred types

Every task output is inferred through the `output` shape.
 - `load_user` output is typed as object with `email: string` field
 - `nudge` output is object with `nudged: boolean` field

The process output is also inferred, the inferred context is
based on where all the `goto: end` are in the process.

### Static checking

We are checking if the expressions are accessing existing properties.
If you make a typo (e.g. `"$: outputs.load_user.emial"`), genroc will throw an error.

### The context of a slot

Each slot can have a bit different context depending on previous tasks and
also its position in the task. For example you can't use `self.result` in action
configuration, because the result is available only after the action has executed.

### Other checks

Genroc also validates switch/goto targets (if the task exists) and also doesn't
allow non-reachable tasks.

## Config

The mechanism which allows usage of environment variables in the process.
You can define `config_schema`, it must be a flat object, e.g.:

```genroc
name: process-with-config
config_schema:
  type: object
  properties:
    server_url:
      type: string
  required: [server_url]
```

You can then provide config properties through environment variables like this:

```sh
# scoped to a single process
GENROC_PROCESS_WITH_CONFIG_SERVER_URL=http://example.project
# or globally for all processes
GENROC_GLOBAL_SERVER_URL=http://example.project
```

You can then access config anywhere in the process expressions.

```genroc
    url: "${config.server_url}/users/${input.user_id}"
```

Genroc is loading and validating config values every time it interacts with the process.
You can define any primitive value type and genroc will validate them and convert.
If the validation doesn't pass, process is not allowed to register.
So if the value is required, you need to set the env before applying the definition (on the server).

### Secrets

In the config you can mark the property as `secret`.

```genroc
name: process-with-config
config_schema:
  type: object
  properties:
    server_token:
      type: string
      secret: true
  required: [server_token]
```

This will redact the secrets leaking into stdout (server logs).
Secrets can still leak into db stored logs or process state - so they will be
visible through `genctl logs` and so on.

The `secret` property can only be used in the config.

## The benefits

Genroc type system ensures validty at two different moments, which compelement each other.

**At registration** - everything is statically checked - all the expressions,
the types it produces, goto targets, reachablity. A typo in the expression never
reaches production. `genctl apply --check-only` runs exactly these checks, so
you can run them in the CI; they happen on the server, so you then know that `apply` will pass.

**At runtime** - the outside data entering the process are always validated.
This will ensure that all the statically checked expressions will recieve data
they expect. And the breaking API changes are detected.

### Scenarios

What is **send** by the fetch is judged by the server; what we recieve is judged
by genroc against the `responses` you declared.

| what changed | how you find out |
|---|---|
| the request is no longer accepted | the server answers `4xx`, caught as `http.400`, `http.404`, … |
| the response body no longer passes validation | `result.invalid` |
| the response gained extra fields | nothing — they are dropped (non-breaking change) |


### Process state upgradability

Because genroc knows what should the state schema look like at every stage
of the process, it can decide if old version of the process is upgradable to
newer version. We will look at this feature later.
