You might be wondering what happens when a fetch action fails? Let's look at that.

```genroc
  - id: load_user
    action:
      type: fetch
      method: get
      url: "https://api.example.com/users/${input.user_id}"
      responses:
        200:
          type: object
          properties:
            email: { type: string }
            activated: { type: boolean }
          required: [email, activated]
        409:
          type: object
          properties:
            user_is_protected: { type: boolean }
    on_error:
      - code: ["http.409"]
        case: "error.data.user_is_protected == true"
        # a known error from the server
        goto: $user-protected
      - code: ["pre.%", "http.timeout", "http.disconnected", "http.503"]
        # server is down, or the connection was aborted
        retry: 3
    switch: next
```

Your main tool is the `on_error` field. It is very similar to `switch` in principle.
You can match one or multiple errors with the `code` field and you can also use `%` wildcard to match multiple errors at once.

## Typed error responses

You can type your error responses the same way as your success responses.
When you do that, you can match the typed error response code and then use `error.data` to use the error response body.

### Case field

If you want to perform an additional check on the error response body, you can use `case` field, which works the same way
as on `switch`, so you can have custom expression returning boolean.

You can also use `case` field alone (without matching the code), but for most cases the `code` field is more convenient.

## Reacting to the error

You can do 2 main things when error happens.

### Retry

This will park the process for some time and will try the fetch again. There are advanced settings for retry as well:

```genroc
retry: 3
# or
retry:
  retries: 3
  delay: "1s"
  factor: 2
  max_delay: "5m"
```

 - `retries` - are **extra** fetches above the default one. So 3 retries can give you 4 failed fetches.
 - `delay` - says how long should we wait before the next retry (`1s` is default)*
 - `factor` - a multiplier of the delay after each retry (`1s`, `2s`, `4s` in this case, 2 is default)
 - `max_delay` - cap to the multiplication (max(`5m`, delay) is default)

> \* we apply (delay/2) randomized jitter to avoid multiple processes hammering the endpoint all at the same time

### Route to another task

If you want the process to continue, you can use `goto` field to route to another task.
The targeted task will have extra `last_error` field available, with the error data. The field is available only to the 
task directly after the error, following tasks won't have access to it.

```genroc
  - id: load_user
    action:
      type: fetch
      ...
    on_error:
      - code: ["http.409"]
        goto: $user-protected
    ...
  - id: user-protected
    # you can access the `last_error` variable
    output:
      is_protected: "$: last_error.data.user_is_protected"
    ...
```

> You can also `panic` or `raise`, but that will get useful once we get to the child processes

## Only once

In certain cases it is important that operation happens exactly once (e.g. money transfers).

Genroc has a primitive for this, called `only_once`.

```genroc
  - id: transfer_money
    action:
      type: fetch
      method: post
      url: "https://api.example.com/money/transfer"
      body:
        from: "$: input.from"
        to: "$: input.to"
        amount: "$: input.amount"
    only_once: true
    on_error:
      - code: ["pre.%"]
        retry: 3
      - code: ["http.503"]
        retry: 3
        not_reached: true
    switch: end
```

In this example we are using `only_once`. In this case genroc is very careful to only hit the endpoint once.
You can safely retry on `pre.%` errors, because those errors happen before the request left (dns lookup, tcp handshake).

You can also retry on other errors, but you have to explicitly add `not_reached` field.
That field is there to make sure you won't retry by accident, genroc will require this, because you have to ensure
that the error actually means the operation was not performed.

### Ambiguous cases

Inherently there are cases when we genuenly cannot know if the operation was performed or not (read about [Two Generals' Problem](https://en.wikipedia.org/wiki/Two_Generals%27_Problem)),
in these cases you either need to check if the money were transferred or not through a different channel.

| Code | Reported by | What happened |
|---|---|---|
| `only_once.interrupted` | any `only_once` task | a previous attempt was interrupted — route it, never retry |
| `http.timeout` | fetch | connected, but no response arrived in time |
| `http.disconnected` | fetch | the request went out, the connection broke before a response |
| `external.timeout` | external | the wait deadline elapsed |
| `external.lost` | external | a worker's claim expired without an answer |

`not_reached` buys nothing here: it asserts what an error *means*, and that is a claim you can only
make about an error that came back. Naming one of these alongside `retry` is refused at registration.

### What to do with ambiguious cases

By default the process will fail and you can manually check if the money went away or not.

Or you can have a idepotent task for checking if the transaction happened or not and then retry based on that.

```genroc
  - id: transfer_money
    action:
      type: fetch
      method: post
      url: "https://api.example.com/money/transfer"
      body:
        from: "$: input.from"
        to: "$: input.to"
        amount: "$: input.amount"
        transatction_id: "$: input.transaction_id"
    only_once: true
    on_error:
      - code: ["only_once.interrupted", "http.timeout", "http.disconnected"]
        goto: $check_transfer
    switch: end
  - id: check_transfer
    action:
      type: fetch
      method: get
      url: "https://api.example.com/money/check_transaction/${input.transaction_id}"
      accepted_status: [2xx, "404"]   # specifies which statuses are not considered error
    output:
      retries: "$: (self.previous.retries ?? 0) + 1"
    switch:
      - case: "self.status == 404 && self.output.retries < 3"
        goto: $transfer_money
      - goto: end
```

This is a bit more complicated example, but basically what we do is
we check if the transaction exists or not in the `check_transaction` task.
We limit the retries to 3 through the output mapping (we are reading previous output.retries and adding one).

## Accepted statuses

In the example above, we've introduced a new field `accepted_status`.
This field defines which http statuses are considered success.

The default value is `2xx`, but there is a caveat when the `responses` field defines an output.

### Responses field influence
If responses field contains 2xx field the accepted statuses are narrowed to only them.

This can feel a bit strange, because if you only define response type for `200`, you can recieve `202` as an error, 
but the logic is that if you've defined the response type, you usually need the data from the body.

If you need to always accept all 2xx statuses regardless of the body, you can override the `accepted_status` manually.
But you then need to count with the case that the body won't be there.


## Fetch error codes

Errors are sorted into families by their prefix:

| Code | Meaning |
|---|---|
| `http.<status>` | a status `accepted_status` did not admit, e.g. `http.404` |
| `http.timeout` | connected, but no response arrived in time |
| `http.disconnected` | the request went out, the connection broke before a response |
| `pre.timeout` | timed out before the request was written — it never left |
| `pre.error` | failed before the request was written — it never left |
| `result.parse` | the response body was not valid JSON |
| `result.too_large` | the response body exceeded the size a fetch will read |
| `result.invalid` | the result did not satisfy the schema declared for it |
| `only_once.interrupted` | this happens if something unexpected happens (e.g. server crash) during the `only_once` task execution and the engine doesn't know if the operation was performed or not |
