Genroc supports child processes, which you can imagine as function calls.
The parent specifies the child's name and its input. The child instance
is then started and the parent instance is parked (its status is still `running`,
but it is effectively waiting for the child to finish). When the child
finishes, its output becomes the task's result.

You can use a child process to reuse a piece of logic in multiple processes,
or as a wrapper for an external system, which allows independent versioning.

## `child` action

Let's define two processes:

```genroc-lsp
# greet.genroc.yaml
name: greet
input_schema:
  type: object
  properties:
    who: {type: string}
  required: [who]
tasks:
  - id: welcome
    output: "Hello, ${input.who}"
    switch: end

output:
  message: "$: outputs.welcome"
```

```genroc-lsp
# parent.genroc.yaml
name: parent_process
tasks:
  - id: spawn_child
    action:
      type: child
      name: greet
      input:
        who: world
      result_schema:
        type: object
        properties:
          message: {type: string}
    output: "$: self.result"
    switch: end

output: "$: outputs.spawn_child.message"
```

The `child` action is quite similar to the `fetch` action, as it also
has an input and a `result_schema`. Additionally, it needs the `name` of the
child process.

Let's now apply the processes and run the parent.

```sh
> genctl apply
latest: greet - -> v1 (new)
latest: parent_process - -> v1 (new)

> genctl run parent_process
started: 3kjfx4vm  parent_process@v1  (running)
```

You can now print logs:

```sh
> genctl logs @last
TIME      LEVEL  ID        EVENT             TASK
--- 2026-09-16 +02:00 ---
14:07:46  INFO   3kjfx4vm  inst_created                      by=no-auth:anonymous
14:07:46  INFO   3kjfx4vm  child_spawned     spawn_child     msg="1 children"
14:07:46  INFO   02pcayvt  inst_created                      input={"who":"world"}
14:07:46  INFO   02pcayvt  inst_completed    welcome         output={"message":"Hello, world"}
14:07:46  INFO   3kjfx4vm  child_collected   spawn_child
14:07:46  INFO   3kjfx4vm  inst_completed    spawn_child     output="Hello, world"
```

This automatically shows the logs of the parent and all its children,
so we can see exactly what happened.

We can also list instances like this:

```sh
> genctl instances
ID        STATUS     PROCESS            UPDATED  CREATED  CODE  ERROR
3kjfx4vm  completed  parent_process@v1  3m ago   3m ago
```

However, this shows only root instances (the instances that have no parent);
we have to add the `--children` parameter to see all of them.

```sh
> genctl instances --children
ID        STATUS     PROCESS            PARENT    UPDATED  CREATED  CODE  ERROR
3kjfx4vm  completed  parent_process@v1  -         3m ago   3m ago
02pcayvt  completed  greet@v1           3kjfx4vm  3m ago   3m ago
```

## `child_map` action

It runs multiple children in parallel,
and they can be of different kinds. You specify each child independently in
the `children` object.

```genroc-lsp
name: checkout
input_schema:
  type: object
  properties:
    order_id: { type: string }
  required: [order_id]
tasks:
  - id: prepare
    action:
      type: child_map
      children:
        stock:
          name: reserve-stock
          input: { order_id: "${input.order_id}" }
          result_schema: { type: boolean }
        payment:
          name: charge-card
          input: { order_id: "${input.order_id}" }
          result_schema: { type: number }
    output: "$: self.result"
    switch: end

output:
  reserved: "$: outputs.prepare.stock"
  charged: "$: outputs.prepare.payment"
```

The parent instance waits for all the children to finish.
The children's outputs are collected into an object mirroring the `children` keys.

## `child_list` action

This one runs a dynamic number of children in parallel; all of them are of the same kind.
The fields are the same as on a single `child`, but instead of `input` there is `over`,
which must be an array of inputs.

```genroc-lsp
name: greet_all
input_schema:
  type: array
  items: { type: string }
  maxItems: 10
tasks:
  - id: prepare
    action:
      type: child_list
      name: greet
      # mapping into Array<object{who}>
      over: "$: map(input, (name) => { who: name })"
      result_schema:
        type: object
        properties:
          message: { type: string }
        required: [message]
    output: "$: self.result"    # result: Array<object{message}>
    switch: end
output:
  result: "$: outputs.prepare"
```

Notice we are using the `map` function to create a properly shaped array.

The `result_schema` applies to each individual item, and the results are collected into an array
in the same order as the inputs.

## Action fields

The three child actions share most of their fields:

| Field           | Used by                         | Meaning                                                                  |
|-----------------|---------------------------------|--------------------------------------------------------------------------|
| `name`          | all                             | The process to start. Required.                                          |
| `version`       | all                             | The version to run; the latest when omitted.                             |
| `input`         | `child`, `child_map` entries    | The child's input.                                                       |
| `over`          | `child_list`                    | An array expression; one child is started per item, with the item as its input. Required. |
| `children`      | `child_map`                     | Named entries, each with the fields above. Required.                     |
| `input_schema`  | all                             | Declares the input sent to the child.                                    |
| `result_schema` | all                             | Declares the child's output, as the parent reads it.                     |
| `raises`        | all                             | The `raise` codes the parent can catch, with their data schemas ([more](#the-raises-field)). |

On `child_map`, each entry under `children` has its own `name`, `version`, `input`, schemas and `raises`.

## Parent/child type checking

Genroc checks the parent/child compatibility when the definitions are applied.
It checks that the inputs you pass fit the child's `input_schema`, and that the child's output and error data fit the parent's `result_schema` and `raises`.

The lsp doesn't check the compatibility between processes locally,
run `genctl apply --check-only` to check on the server.

## Child error handling

Genroc doesn't use classic "catching" for child processes. The main reason is that we require
everything to be explicitly typed, and processes should be self-contained in terms of their interface.

So every process needs to explicitly specify which errors it can produce. This is also
the reason why errors don't bubble up through the tree: if they did, a process would
leak types from its children, which we don't allow.

Raised errors are understood as a branching tool for expected failures.

```genroc
# child (fetch action)
on_error:
  - code: ["http.404"]
    raise:
      code: "item_not_found"
      message: "Item ${input.item_id} not found"

# parent (child action)
raises:
  item_not_found: null  # we need to specify explicitly what errors we expect
on_error:
  - code: ["item_not_found"]
    goto: $handle_item_not_found
```

> Read more about `panic` and `raise` in the [error handling](./error-handling.mdx#panic) section.

### The `raises` field

Specifies which errors we expect. It's an object whose keys are error codes and whose values are (optional) JSON schemas.
If you define an error schema, you can then access `error.data` (like with `fetch` error responses).

## Importing child process

You can import a child process to avoid duplicating its fields in the YAML.

```genroc
# parent.genroc.yaml
name: parent_process
tasks:
  - id: spawn_child
    action:
      type: child
      <<: "$process: ./child.genroc.yaml"
      input:
        who: world
    output: "$: self.result"
    switch: end
output: "$: outputs.spawn_child.message"
```

`$process:` is a resolver: it finds the specified genroc file,
builds its types and returns `name`, `input_schema`, `result_schema` and `raises`.

### `<<` operator

The `<<` operator is the YAML convention for spread syntax.

It is used to prefill an object with default values. Genroc
expands the resolver into the object. The equivalent pure YAML
would look like this:

```genroc
  - id: spawn_child
    action:
      type: child
      <<:
        # product of `$process: ./child.genroc.yaml`
        name: greet
        result_schema:
          type: object
          properties:
            message: {type: string}
      input:
        who: world
```
