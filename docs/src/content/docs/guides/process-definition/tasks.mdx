To make our process actually do something, we need a way how to communicate with
outside world and that is where the task `action` comes in.

Let's say we want to send our users email two ours after registration and welcome
them.

```genroc
name: welcome-user
input_schema:
  type: object
  properties:
    user_email:
      type: string
  required: [user_email]

tasks:
  - id: wait-some-time
    action:
      type: delay    # process will be parked for 2 hours
      for: 2h
    switch: next

  - id: welcome
    action:
      type: fetch    # this will hit endpoint on our API
      url: "https://api.example.com/emails"
      method: post
      body:
        # passing data from input to the request body
        to: "$: input.user_email"
        template: welcome-after-registration
    switch: end
```

In the example above we've used `delay` and `fetch` actions.
The delay will park the action for specified amount of time, while it waits there is no active thread anywhere, it just sits in the db.

The fetch action will then hit the specified endpoint. We are sending body with parameters which can be either expressions or static data.

## Reading result of the fetch

What if instead of sending data, you want to read data? No problem, let's look at another example.

```genroc
  - id: load_user
    action:
      type: fetch
      method: get
      url: "https://api.example.com/users/${input.user_id}"
      responses:
        200:
          type: object
          properties:
            email: { type: string }
            activated: { type: boolean }
          required: [email, activated]
    switch:
      - case: "self.result.activated"
        goto: end
      - goto: $nudge
    # mapping the task output (what parts of the response we need)
    output:
      email: "$: self.result.email"
```

To read the output of fetch, you need to specify it's response type.
Genroc will validate the data against the schema, so no invalid data will ever get in.

Result of the fetch is then available as `self.result` in the `case` expression,
so we can check if the account is activated or not.

`self.result` is only usable within the same task. If we want to use some data later (in following tasks),
we have to map it through output. In this case we are producing output `{ email: '<user email>'}` which will then
be available to following tasks under `outputs.<task-id>`.
