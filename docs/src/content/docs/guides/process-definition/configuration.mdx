Genroc allows you to pass environment variables through the `config` property.

## Specifying `config_schema`

If you want to use `config` in your process, you first need to
specify what values and types you require for the process.

This is done through `config_schema`, it takes a JSON Schema.
It is similar to `input_schema`, however it only supports a
flat object with primitive properties (as it's coming from env and
nested properties would be awkward here).

```genroc-lsp
name: get-user-data
input_schema:
  type: object
  properties:
    user_id: { type: string }
  required: [user_id]

config_schema:
  type: object
  properties:
    server_origin:
      type: string
      default: "http://localhost:8080"
    server_auth:
      type: string
      secret: true
  required: [server_auth]

tasks:
  - id: load_user
    action:
      type: fetch
      method: get
      url: "${config.server_origin}/users/${input.user_id}"
      headers:
        Authorization: "Bearer ${config.server_auth}"
    switch: end
```

### Specifying the env

Values come from the environment of the genroc server (not genctl). Each property is read
from a variable named after the process, or from a global one shared by all processes:

```sh
# only for get-user-data
GENROC_GET_USER_DATA_SERVER_AUTH=secret-token
# for every process with a server_origin property
GENROC_GLOBAL_SERVER_ORIGIN=https://api.example.com
```

Names are upper-cased, with `-` turned into `_` and camelCase split (`serverAuth` reads
`SERVER_AUTH`). Property names must be identifiers (letters, digits and `_`), and two
properties that map to the same variable, like `apiKey` and `api_key`, are refused.
The process variable wins over the global one, and an empty variable counts
as unset. Without either, the `default` is used.

Values are converted to the declared type, so for a property declared as `integer`,
`GENROC_GLOBAL_RETRIES=3` arrives as a number
and `true`/`false` as a boolean. A required value that's missing, or one that doesn't
convert, is refused by `genctl apply` and when a process starts. Genroc reads the values again
on every step and never stores them, so after you change one and restart the server, running
processes use the new value too. If a value goes missing or stops converting, the process
fails at its next step with `engine.config`.

### Secrets

`config_schema` is also special, because you can mark
a string property as `secret`. This keeps the value out of
the server's console output.

The value can however still leak into db logs accessible through
`genctl logs` or into the process state.

Genroc replaces the exact value with `***` in the console output of the process that declares it.
That works because expressions can't transform a string, so a secret only ever appears
verbatim, like in `Bearer <token>`. Redaction doesn't reach the input logged when the process
starts, or the console output of a child process you pass the secret to.
